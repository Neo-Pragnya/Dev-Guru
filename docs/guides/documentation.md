# Documentation and explanations

Dev Guru writes documentation from what Ananke finds in the code. Nothing is generated by a language model, so the
same code always gives the same words, and every statement links to the file and line it comes from.

## Explain one thing at four levels

```bash
dev explain cart.py                 # a file
dev explain total                   # a function or class, by name
dev explain shop/cart.py:total      # path:name when a name is used twice
dev explain cart.py -l novice -l executive -o cart.md
dev explain cart.py --json          # dev-guru/explanation@1
```

| Level | Written for | What it says |
| --- | --- | --- |
| `novice` | someone new to the code | what it is, what it's for (from its own docstring), what it defines, what it uses |
| `practitioner` | developers | signatures, what it imports, who calls it and what it calls, with the lines |
| `principal` | architects and reviewers | how many files depend on it, directly or not; import cycles; complex functions |
| `executive` | leaders | how central it is, and whether anything about it is risky, in a sentence |

Each statement has a **basis**: *observed* (read from the code), *derived* (counted from what was observed) or
*inferred* (a call Ananke resolved through imports, which dynamic code can defeat). Inferred statements are marked.

## Documentation for an audience

```bash
dev docs . --audience novice                         # dev-guru-novice.md
dev docs . --audience practitioner --detail deep -o docs/code-guide.md
dev docs . --audience principal -o docs/architecture-notes.md
dev docs . --audience executive -f deck -o review.html   # an offline slide deck
dev docs . --audience executive -f slides                # Markdown for dev present, to edit first
```

| Audience | Sections |
| --- | --- |
| `novice` | summary, words used here, where to start (a reading order), the files most others use, limits |
| `practitioner` | summary, where to start, every folder's files and what they define, API routes, data tables, complex functions, limits |
| `principal` | summary, folders and their dependencies, the files the rest depends on, where the risk is, routes, tables, complexity, limits |
| `executive` | summary, where the risk is (cycles, complex functions, central files, test coverage, vulnerabilities), limits |

`--detail` is `brief` (5 rows a section), `standard` (15) or `deep` (50, and each file's developer-level notes).

Every document ends with its **provenance**: the Git revision (and whether it had uncommitted changes), the Ananke
and Dev Guru versions, and the digest of the model it came from. A manifest with the file's sha256 is written next to
it (`<file>.manifest.json`). Links are relative, so write the document inside the project and they work on GitHub and
on a docs site. Before a file is kept, every link is checked; a broken one is an error, not a warning.

Text from the code (docstrings, names, signatures) is escaped, so a docstring can't add a link, HTML or a table cell.

## Limits

- Python is analysed in full; other languages contribute what the repository analysis finds (routes, tables,
  complexity), not calls.
- Test coverage and vulnerabilities are reported only when a coverage file exists or `--check-vulnerabilities` was
  used; otherwise the document says they're unknown, never that they're fine.
